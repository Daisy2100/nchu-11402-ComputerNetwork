## 1. What are the header fields to identify a UDP socket and a TCP socket?

### UDP Socket（二元組）
UDP socket 由以下 **2 個欄位** 識別：

| 欄位 | 說明 |
|------|------|
| **目的地 IP 位址** (Destination IP) | 封包要送達的主機位址 |
| **目的地埠號** (Destination Port) | 目的地主機上的應用程式埠號 |

> **注意**：兩個來源不同（不同來源 IP 或來源埠）的 UDP 封包，只要目的地 IP 和埠號相同，就會被導向同一個 UDP socket。

### TCP Socket（四元組）
TCP socket 由以下 **4 個欄位** 識別：

| 欄位 | 說明 |
|------|------|
| **來源 IP 位址** (Source IP) | 發送端主機位址 |
| **來源埠號** (Source Port) | 發送端應用程式埠號 |
| **目的地 IP 位址** (Destination IP) | 接收端主機位址 |
| **目的地埠號** (Destination Port) | 接收端應用程式埠號 |

> **注意**：TCP 用四元組區分不同連線。即使目的地相同，只要來源 IP 或來源埠不同，就是不同的 TCP socket（連線）。

## 2. Please describe the mechanism of packet error detection using checksum.

### 發送端（Sender）步驟
1. 將要傳送的資料切成多個 **16-bit 的字組（segment）**。
2. 將所有 16-bit 字組進行 **一補數加法（1's complement sum）**。
   - 若相加產生進位（carry），需將進位位元加回最低位元（wraparound）。
3. 對加總結果取 **一補數（反轉所有位元）**，得到 checksum。
4. 將 checksum 放入 UDP/TCP 標頭的 checksum 欄位，連同資料一起傳送。

### 接收端（Receiver）步驟
1. 收到封包後，將所有 16-bit 字組（包含 checksum 欄位）再次進行一補數加法。
2. 若結果為 **全 1（1111...1）**，表示傳輸**無誤**。
3. 若結果中有任何 **0**，表示傳輸**發生錯誤**。

### 原理說明
一補數加法的特性：正確資料加上其 checksum 的結果會是全 1，任何位元翻轉都會破壞這個結果。

## 3. Please calculate the checksum of the following two 16-bit binary integers:
1110011001100110 &amp; 1101010101010101.


計算以下兩個 16-bit 整數的 checksum：
- **A** = `1110011001100110`
- **B** = `1101010101010101`

### 步驟一：二進位加法

```
  1110011001100110
+ 1101010101010101
─────────────────
```

逐位相加：

```
  1110011001100110
+ 1101010101010101
─────────────────
 11011101110111011   ← 產生第17位元的進位（carry = 1）
```

### 步驟二：Wraparound（進位加回）

將進位的 1 加回最低位元：

```
  1011101110111011
+                1
─────────────────
  1011101110111100
```

### 步驟三：取一補數（反轉所有位元）

```
  1011101110111100
→ 0100010001000011  ← 這就是 Checksum
```

### 驗證
```
  1110011001100110
+ 1101010101010101
+ 0100010001000011
─────────────────
= 1111111111111111  ✓ 全 1，正確！
```

**Checksum = `0100010001000011`**

## 4. Please list the network applications of UDP.

UDP 適合對**速度要求高、可容忍少量遺失、不需要連線建立**的應用：

| 應用類別 | 具體例子 |
|----------|----------|
| **串流多媒體** | 即時視訊串流、音訊串流（如 YouTube 直播） |
| **網路電話（VoIP）** | Skype、Zoom 語音通話 |
| **DNS 查詢** | 域名解析（Domain Name System） |
| **線上遊戲** | 即時多人遊戲（需要低延遲） |
| **網路管理** | SNMP（Simple Network Management Protocol） |
| **路由協定** | RIP（Routing Information Protocol） |
| **廣播 / 多播** | 一對多的資料傳送 |
| **DHCP** | 動態 IP 位址分配 |
| **TFTP** | 簡單檔案傳輸協定 |

**選擇 UDP 的原因：**
- 無需握手（no handshaking），延遲低
- 不維護連線狀態，開銷小
- 可自行在應用層實作所需的可靠性

## 5. Please describe all necessary mechanisms to recover the packets with bit errors.

要從位元錯誤中恢復，需要以下三大機制：

### 機制一：錯誤偵測（Error Detection）
- 使用 **Checksum** 偵測資料是否在傳輸中發生位元翻轉。
- 接收端計算收到資料的 checksum，若不符合則判定為錯誤封包。

### 機制二：接收端回饋（Receiver Feedback / ACK & NAK）
- **ACK（Acknowledgement）**：接收端告知發送端「封包正確收到」。
- **NAK（Negative Acknowledgement）**：接收端告知發送端「封包有錯誤，請重傳」。
- 現代協定（如 TCP）通常只使用 ACK，用重複 ACK 或逾時來隱式表達 NAK。

### 機制三：重傳（Retransmission）
- 發送端收到 NAK，或在設定的 **計時器（Timer）** 超時後未收到 ACK，則重新傳送該封包。

### 附加考量：序號（Sequence Number）
- 若 ACK/NAK 本身也發生位元錯誤，發送端無法判斷，可能會重傳導致接收端收到重複封包。
- 使用**序號**讓接收端辨別封包是新資料還是重傳，以避免重複接收。

## 6. Please explain why one-bit sequence number is enough for a stop-and-wait protocol.

### Stop-and-Wait 的運作方式
- 發送端每次只傳送 **1 個封包**，並等待 ACK 後才傳下一個。
- 在任何時刻，網路中**最多只有 1 個未被確認的封包**。

### 為何 1-bit 就夠
- 1-bit 序號可以表示 **0** 和 **1** 兩個值，剛好夠用。
- 接收端只需知道當前等待的封包是 0 號還是 1 號：
  - 若收到的封包序號與期望相同 → 新資料，接受並發送 ACK。
  - 若收到的封包序號與期望不同 → 重傳的舊資料，丟棄並重發 ACK。
- 由於同一時間只可能有 0 或 1 號封包在網路上，1-bit 完全足夠區分「當前封包」與「上一個重傳封包」。

## 7. What is the function of sequence numbers in feedback segments?

### 功能：解決 ACK/NAK 本身損壞的問題

當發送端收到損壞的 ACK/NAK 時，它不知道接收端的狀態，只能選擇重傳。但重傳可能導致接收端收到**重複的封包**。

**ACK 中的序號功能如下：**

1. **確認對應封包**：ACK 中的序號告訴發送端「我確認收到了第 N 號封包」，讓發送端精確知道哪個封包被成功接收。

2. **讓接收端辨別重複封包**：若接收端已收到封包 0 並回了 ACK0，發送端因 ACK 損壞而重傳封包 0，接收端看到序號 0 就知道這是重複封包，直接丟棄並再次回 ACK0，不會把它當成新資料處理。

3. **讓發送端辨別 ACK 對應的封包**：在流水線協定中，ACK 的序號明確指出哪個封包已送達，讓發送端可以滑動視窗。

## 8. Please describe all necessary mechanisms to recover packet loss.

要從封包遺失中恢復，需要以下機制：

### 機制一：計時器（Timer / Timeout）
- 發送端傳送封包後，啟動一個計時器。
- 若在計時器到期前未收到 ACK，發送端判定封包（或 ACK）已遺失，執行**重傳**。

### 機制二：重傳（Retransmission）
- 超時後，發送端重新傳送未被確認的封包。

### 機制三：序號（Sequence Number）
- 由於重傳可能造成接收端收到重複封包，序號用來讓接收端區分新封包與重複封包，避免重複交付給上層應用。

### 流程圖（文字版）
```
發送端傳送封包 → 啟動計時器
    ↓
收到 ACK？
  是 → 關閉計時器，傳下一個封包
  否（Timeout）→ 重傳封包，重啟計時器
```

## 9. Please describe the problems caused by improper timeout values.

### 情況一：Timeout 值過短（Too Short）
- 發送端在 ACK 還沒到達前就超時，觸發**不必要的重傳（Unnecessary Retransmission）**。
- 問題：
  - 浪費網路頻寬（傳輸重複資料）
  - 增加網路擁塞
  - 降低傳輸效率

### 情況二：Timeout 值過長（Too Long）
- 發送端等待很久才判定封包遺失，導致**恢復速度緩慢**。
- 問題：
  - 封包遺失後，長時間閒置等待，浪費時間
  - 鏈路使用率低
  - 傳輸延遲大（尤其對互動式應用影響大）

### 理想的 Timeout 值
- 應略大於 **RTT（Round-Trip Time，來回時間）**。
- 但 RTT 會隨網路狀況波動，因此 TCP 使用**動態估算**（見第 13 題）。

## 10. The performance of the stop-and-wait protocol is poor and can be improved by a pipelining protocol. Please describe the idea of the pipelining protocol.

### Stop-and-Wait 的問題
- 每次只傳一個封包，然後等待 ACK，鏈路使用率極低。
- 使用率（Utilization）= `(傳輸時間) / (傳輸時間 + 2×傳播延遲)` ≈ 非常小

### 流水線協定的核心思想
- **允許發送端在未收到 ACK 的情況下，連續傳送多個封包**。
- 設定一個「**視窗大小（Window Size = N）**」，最多允許 N 個封包同時在途（in-flight）。

### 效益
- 鏈路使用率大幅提升：使用率 ≈ `N × (傳輸時間) / (傳輸時間 + 2×傳播延遲)`
- 若 N 夠大，可接近 100% 的鏈路使用率

### 流水線協定的兩大實作
- **Go-Back-N（GBN）**
- **Selective Repeat（SR）**

### 圖示（文字版）
```
Stop-and-Wait：[封包1] → 等待 → [封包2] → 等待 → ...
流水線：       [封包1][封包2][封包3][封包4] → 等待 ACK（同時在途）
```

## 11. Please describe the difference between Go-Back-N and Selective Repeat for packet retransmission, receiver window (buffer) size, and number of timers.


| 比較項目 | Go-Back-N (GBN) | Selective Repeat (SR) |
|----------|-----------------|----------------------|
| **封包重傳** | 發生遺失時，重傳**遺失封包及之後所有封包** | 只重傳**遺失的那個封包** |
| **接收端視窗大小** | **1**（只接受按序到達的封包，亂序封包直接丟棄） | **W**（可緩衝亂序到達的封包） |
| **接收端緩衝區** | 不需要（無緩衝） | 需要大小為 W 的緩衝區 |
| **計時器數量** | **1 個**（只為最舊的未確認封包計時） | **N 個**（每個未確認封包都有獨立計時器） |
| **優點** | 實作簡單 | 網路效率高，不浪費頻寬重傳已收到的封包 |
| **缺點** | 封包錯誤時重傳大量封包，浪費頻寬 | 實作複雜，需要較多緩衝記憶體 |

### Go-Back-N 重傳示意
```
發送: [1][2][3][4][5]
封包3遺失
重傳: [3][4][5]  ← 3之後全部重傳
```

### Selective Repeat 重傳示意
```
發送: [1][2][3][4][5]
封包3遺失，4、5先緩衝
重傳: [3]  ← 只重傳3
```

## 12. How many sequence numbers are required for selective repeat? (window size=W)

### 結論
視窗大小為 **W** 時，Selective Repeat 需要至少 **2W 個序號**。

### 推導
- 發送視窗大小 = W，接收視窗大小 = W
- 為了避免接收端無法區分「新封包」與「舊的重傳封包」，序號空間必須夠大。
- 若序號空間 < 2W，當所有 ACK 遺失，發送端重傳舊封包時，接收端可能誤以為是新封包。

**條件：序號空間 ≥ 2W**

即：若以位元數 k 表示序號，則 $2^k \geq 2W$，即 $k \geq \log_2(2W)$。

> 對比：Go-Back-N 只需序號空間 ≥ W+1。

## 13. Please introduce the basic idea of calculating TCP timeout value.

TCP 使用**動態估算**的方式計算 Timeout，主要基於 **EstimatedRTT** 和 **DevRTT**。

### 步驟一：測量 SampleRTT
每次傳送封包並收到 ACK，記錄一次實際的來回時間 `SampleRTT`。

### 步驟二：計算 EstimatedRTT（指數加權移動平均）
$$\text{EstimatedRTT} = (1-\alpha) \times \text{EstimatedRTT} + \alpha \times \text{SampleRTT}$$
- 通常 $\alpha = 0.125$（即 1/8）
- 這會使 EstimatedRTT 隨時間平滑地跟隨網路變化

### 步驟三：計算 DevRTT（RTT 的偏差/抖動）
$$\text{DevRTT} = (1-\beta) \times \text{DevRTT} + \beta \times |\text{SampleRTT} - \text{EstimatedRTT}|$$
- 通常 $\beta = 0.25$（即 1/4）
- 衡量 RTT 的波動程度

### 步驟四：計算 Timeout 值
$$\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \times \text{DevRTT}$$
- 加上 4 倍偏差作為安全餘量，避免不必要的超時
- 網路抖動大時，Timeout 自動變大

## 14. Please describe the procedure of TCP delayed ACK in TCP receivers.

### 基本規則
TCP 接收端**不需要每收到一個封包就立刻回 ACK**，而是採用延遲策略：

### 詳細程序

1. **等待下一個封包**：收到一個按序（in-order）封包後，等待最多 **500ms**。
   - 若在此時間內收到下一個按序封包 → 一次回 **一個 ACK**（累積確認兩個封包）。
   - 若 500ms 內沒有下一個封包 → 立刻回 ACK。

2. **連續收到兩個按序封包**：立刻回 **一個 cumulative ACK**（確認兩個）。

3. **收到亂序封包（gap）**：立刻回 **duplicate ACK**，通知發送端有封包遺失。

4. **填補缺口（gap filled）**：收到可填補缺口的封包後，立刻回 ACK。

### 目的
- 減少 ACK 封包數量，降低網路負擔
- 通常可以讓 ACK 搭載在反向資料封包中（Piggybacking）


## 15. Please describe the idea of TCP Fast Retransmit.

### 問題背景
等待 Timeout 才重傳，延遲太長。TCP 提供更快的機制。

### 核心概念
- 當接收端收到**亂序封包**（out-of-order）時，會立刻回 **Duplicate ACK**（重複 ACK，確認號與上一個相同）。
- 發送端若連續收到 **3 個相同的 Duplicate ACK**（即第 3 個重複 ACK，共收到 4 個相同 ACK），判定對應封包已遺失。
- **不等待 Timeout**，立刻重傳該封包。

### 流程
```
接收端收到: [1] [2] [4] [5] [6]  ← 3遺失
接收端回:  ACK2, ACK2, ACK2, ACK2  ← 3個Duplicate ACK

發送端收到3個Duplicate ACK → 立刻重傳封包3（不等Timeout）
```

### 優點
- 比等待 Timeout 快得多，大幅降低遺失封包的恢復時間
- 減少不必要的等待，提升吞吐量

## 16. TCP flow control can avoid receiver buffer overflows. Please describe its procedure.
### 目的
防止**發送端傳送速度過快**，導致接收端的**接收緩衝區溢出（overflow）**。

### 機制：接收視窗（Receive Window, rwnd）

1. **接收端**在每個 ACK 標頭中，填入 `rwnd`（Receive Window）欄位，告知發送端目前緩衝區剩餘空間：
   $$\text{rwnd} = \text{RcvBuffer} - (\text{LastByteRcvd} - \text{LastByteRead})$$

2. **發送端**保證「已傳送但未收到 ACK 的資料量」不超過 `rwnd`：
   $$\text{LastByteSent} - \text{LastByteAcked} \leq \text{rwnd}$$

3. 若接收端緩衝區滿（`rwnd = 0`），發送端**停止傳送**，但定期傳送 1-byte 的探測封包，等待接收端緩衝區釋放空間。

### 圖示
```
接收端緩衝區: [已讀取] [待處理] [空閒 = rwnd]
發送端限制傳送量 ≤ rwnd
```

## 17. Please describe the difference of reliable data transfer between TCP and Go-Back-N.

| 比較項目 | Go-Back-N | TCP |
|----------|-----------|-----|
| **重傳策略** | 遺失封包及其後所有封包全部重傳 | 通常只重傳**遺失的那個 segment**（類似 SR） |
| **接收端緩衝** | 不緩衝亂序封包，直接丟棄 | **緩衝**亂序到達的 segment |
| **ACK 類型** | 累積確認（Cumulative ACK） | 累積確認（Cumulative ACK） |
| **計時器** | 1 個（針對最舊未確認封包） | 通常 1 個（針對最舊未確認 segment） |
| **快速重傳** | 無 | 有（3 個 Duplicate ACK 觸發） |
| **視窗控制** | 固定視窗 | 動態（受 rwnd 和 cwnd 雙重控制） |

### 關鍵差異說明
- TCP 雖然使用累積 ACK（類似 GBN），但它**緩衝亂序封包**（類似 SR），不會重傳已正確收到的封包。
- TCP 的重傳行為更接近 **Selective Repeat**，但 ACK 機制類似 GBN。


## 18. Please explain the values specified in fields of sequence number and acknowledge number in a TCP header.

### 序號（Sequence Number）
- 代表**該 segment 中第一個資料 byte 的編號**（以位元組為單位）。
- 例：若目前 Sequence Number = 1000，且 segment 含 500 bytes，則這 500 bytes 的編號為 1000～1499。
- **連線建立時（SYN）**：序號為隨機選取的初始序號（ISN, Initial Sequence Number），不代表資料。

### 確認號（Acknowledgement Number）
- 代表**接收端期望收到的下一個 byte 編號**（即「已成功收到的最後一個 byte + 1」）。
- 例：若 ACK Number = 1500，表示接收端已收到 1～1499 的所有 bytes，期望下一個是 1500。
- ACK 是**累積確認（Cumulative ACK）**：確認號之前的所有資料均已正確收到。

### 範例
```
主機 A → 主機 B：Seq=42, Data="C" (1 byte)
主機 B → 主機 A：Seq=79, ACK=43 (確認收到42，期望下一個是43)
主機 A → 主機 B：Seq=43, ACK=80
```


## 19. TCP uses three-way handshake for connection setup. Why is two-way handshake not used?

### 兩次握手的問題
兩次握手（只有 SYN 和 SYN-ACK）**無法確保雙方都同意連線建立**，存在以下問題：

**問題：舊的重複連線請求（Old Duplicate SYN）**
1. 用戶端發送 SYN，但因網路延遲，SYN 在網路中停留很久。
2. 用戶端超時，重新建立連線並完成資料傳輸後，連線關閉。
3. 舊的 SYN 突然到達伺服端，伺服端以為是新連線，回應 SYN-ACK。
4. 若只有兩次握手，伺服端會認為連線建立，但用戶端早已不認識這個連線，導致伺服端資源浪費或資料混亂。

### 三次握手的解決方案
- 第三次握手（用戶端回 ACK）讓伺服端確認「用戶端確實收到了我的 SYN-ACK，並且認可這個連線」。
- 若是舊的 SYN，用戶端收到 SYN-ACK 時會發現序號不對應，回 RST 拒絕連線，伺服端收到 RST 後放棄連線。

### 三次握手流程
```
Client → Server：SYN (seq=x)
Server → Client：SYN-ACK (seq=y, ack=x+1)
Client → Server：ACK (ack=y+1)  ← 連線建立
```

## 20. Please describe the four-way handshake of closing a TCP connection.

TCP 連線是**全雙工（Full-Duplex）**，雙方各自獨立關閉自己的傳送方向，因此需要四次。

### 流程詳解

```
Client                          Server
  |                               |
  |──── FIN (seq=x) ─────────────>|  ① Client 說：我不再傳資料了
  |                               |
  |<─── ACK (ack=x+1) ───────────|  ② Server 確認（此時 Server 可能還有資料要傳）
  |                               |
  |<─── FIN (seq=y) ─────────────|  ③ Server 說：我也不再傳資料了
  |                               |
  |──── ACK (ack=y+1) ───────────>|  ④ Client 確認
  |                               |
  [Client 等待 2×MSL（TIME_WAIT）]
  |                               |
  連線完全關閉
```

### 各步驟說明
1. **FIN（Client→Server）**：Client 完成資料傳送，發 FIN 關閉自己的傳送方向。
2. **ACK（Server→Client）**：Server 確認收到 FIN，但 Server 可能還有資料要傳（半關閉狀態）。
3. **FIN（Server→Client）**：Server 也完成傳送，發 FIN 關閉自己的傳送方向。
4. **ACK（Client→Server）**：Client 確認收到 Server 的 FIN。

### TIME_WAIT 狀態
- Client 回 ACK 後，進入 **TIME_WAIT** 狀態，等待 **2×MSL（Maximum Segment Lifetime）**。
- 目的：確保最後的 ACK 若遺失，Server 可以重傳 FIN，Client 可再次回 ACK。


## 21. Please describe how TCP slowstart phase adjusts CWND value.

### 基本概念
- **CWND（Congestion Window，擁塞視窗）**：發送端可以在未收到 ACK 的情況下傳送的最大資料量。
- 慢速啟動用於剛建立連線或從擁塞中恢復時，**逐步探測網路可用頻寬**。

### Slow Start 的 CWND 調整規則

1. **初始值**：CWND = 1 MSS（Maximum Segment Size）
2. **每收到一個 ACK**：CWND 增加 1 MSS
   - 等效於：每個 RTT，CWND **翻倍（×2）**，即**指數成長**

### 增長過程
```
初始：      CWND = 1 MSS
第 1 RTT：  CWND = 2 MSS（收到1個ACK→+1，共發2個→收到2個ACK→+2）
第 2 RTT：  CWND = 4 MSS
第 3 RTT：  CWND = 8 MSS
...
```

### 停止條件
- **達到 ssthresh（慢速啟動門檻值）**：停止指數增長，改為**線性增長（擁塞避免）**。
- **發生 Timeout（封包遺失）**：
  - ssthresh = CWND / 2
  - CWND = 1 MSS，重新開始 Slow Start
- **收到 3 個 Duplicate ACK**：
  - ssthresh = CWND / 2
  - CWND = ssthresh（進入擁塞避免，TCP Reno）或 CWND = 1（TCP Tahoe）


## 22. Please describe the idea of AIMD (additive increase; multiplicative decrease) in TCP for adjusting CWND.


### 概念
AIMD 是 TCP 擁塞控制在**擁塞避免（Congestion Avoidance）**階段的核心演算法，目標是在不過度擁塞網路的情況下，最大化頻寬使用率。

### Additive Increase（加法增加）
- 當 CWND ≥ ssthresh 且網路正常時：
- **每個 RTT，CWND 增加 1 MSS**（線性增長）
- 等效：每收到一個 ACK，CWND 增加 `MSS × (MSS/CWND)`（每 RTT 共增加 1 MSS）

```
RTT 1：CWND = 10 MSS
RTT 2：CWND = 11 MSS
RTT 3：CWND = 12 MSS
...（緩慢線性增加）
```

### Multiplicative Decrease（乘法減少）
- **偵測到擁塞（Timeout）時**：
  - CWND = 1 MSS（乘以極小值）
  - ssthresh = CWND_old / 2
- **偵測到輕微擁塞（3 個 Duplicate ACK，TCP Reno）時**：
  - CWND = CWND / 2（乘以 1/2）
  - ssthresh = CWND（新值）

### AIMD 的鋸齒波（Sawtooth）模式
```
CWND
 ↑
 |        /|        /|
 |       / |       / |
 |      /  |      /  |
 |     /   |     /   |
 |    /    ↓    /    ↓
 |___/    擁塞  /   擁塞
 +──────────────────→ 時間
```

### 為何 AIMD 有效？
- **加法增加**：謹慎探測，避免突然大量增加造成擁塞。
- **乘法減少**：快速降低傳送速率，給網路喘息空間。
- 多個 TCP 連線共用網路時，AIMD 能引導各連線趨向**公平分享頻寬（Fairness）**。
